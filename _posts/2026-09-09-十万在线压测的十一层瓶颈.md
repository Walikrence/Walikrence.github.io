> 背景脱敏：某出海棋牌项目，Go 微服务 + MySQL + Redis + Kafka，四节点 K8s 集群。压测用机器人客户端在集群内投放，目标是 10 万在线。这一轮跨度约两周，从 1.3 万在线撮合拐点开始，最终探到 15 万峰值。本文记两件事：瓶颈是怎么一层一层剥开的，以及在归因上犯过的三类同源错误。

## 现象：拐点在 1.3 万，与算力无关

首轮 3 万压测的资源画像给出一个反直觉的事实：撮合 P99 从 5k 在线的 0.49 秒，到 7k 的 1.86 秒，到 13k 的 7.74 秒，16k 后陡增到 23～27 秒；而撮合服务 CPU 峰值只有 1.04 核。拐点在 1.3 万，瓶颈不在算力。

后来的每一层也都是这个形态：CPU 不高，但某个串行点、某把锁、某条同步链把吞吐钉死。

## 十一层瓶颈

按剥开的顺序：

**1. 房间管理单副本是唯一串行阀门。** 撮合的 `AssignPlayers` 是同步 gRPC，慢了就占满撮合侧 16 个并发窗，且 assign 用 `context.Background()` 无超时，慢调用永久占位，单池每 tick 只能排 16 桌，队列指数积压。参数化并发、加超时、连接复用后 13k 拐点消失。

**2. MySQL prepare/execute/close 三连。** 500 人登录窗口做 global status 差分，`Com_stmt_prepare` 增量（+16123）竟不低于 `Com_stmt_execute`（+14565）：驱动默认每条 SQL 三次往返，prepare 本身占近半 Questions。DSN 加 `interpolateParams=true`，同水位主库 QPS 下降 77%，业务节点 CPU 砍半。注意 digest 表看不到 prepared 流量，差分口径必须用 global status。

**3. 消费吞吐被「回源延迟 × 并发」钉死。** 域事件消费实测 236/s ≈ 128 并发 ÷ 519ms 回源，冷缓存下 1.5 万在线即积压 15 万并触发限流自锁。worker 16→64 后 3 万满员时积压自愈。

**4. 回填 99% 耗时是锁排队，不是读库。** 先埋分段直方图再动刀：回填 P99 773ms 里 flush 段占 99%——全部 worker 在一把互斥锁上排队、空跑 `FOR UPDATE` 事务，MySQL 读只有 12ms。锁外一次 EXISTS 判空短路，P99 降到 16.7ms。如果按猜测去做「批量 SELECT IN」，会修错方向。

**5. 建号慢路径成了在线顶。** 预建账号池耗尽后建号退化到 160/s，58k 平台期登录解析账号超时链就是它。拆成三实例后池路径达到 2000/s（峰值 2470）。

**6. 登录整形。** 预热消除回填风暴后暴露一个新事实：回源等待此前一直充当隐形的登录节流，预热让登录吞吐翻倍，反而把数据库洪峰压得更尖。投放模式定稿为「预热 + N 批 × 2500～5000 人 × 45 秒错峰」，并把主库 QPS 与消费积压做成投放双门控。

**7. 撮合的全池栅栏。** 撮合 ticker 用 `wg.Wait` 等所有池，单个慢池把所有池的节奏从 1 秒拖到慢池耗时。改为每池独立协程 + 池级 inflight 守卫，3 万满载下 P99 从 29.4 秒降到 2 秒。8 万时又回升——栅栏解决了「慢池拖累别人」，单池自身排空成了下一层。

**8. 进房 N+1 与登录副作用链。** 登录后串行 8～10 次 gRPC 加支付侧滚动窗 SUM，3 万并发时打满下游再反压回登录关键路径，网关 5 秒超时拒进厅。砍掉无配表依赖的滚动窗查询、进房链路的 N+1 调用合并，与预热一起验收。

**9. 域事件批量消费。** 一次「落库化」改造把每事件的 Redis Lua（约 0.1ms）换成两条同步 SQL 的 CAS，消费 1450/s 小于产生 5000/s，3 万在线积压破百万。修法是消费侧先逐条判定、再按场景聚合 delta，每批每场景一次 CAS（N→1），百万积压秒级消化。

**10. WAL group-commit。** 跨消费批攒窗 20ms 或 500 行一次 InsertMulti，满载积压斜率降约 2/3，在线首次破 10 万（102,164）。但把 grace 压到 2ms 时反而锁雪崩：insert 频率被打回独立小写量级，与后台 flush 在同一张表互等，`Lock wait timeout` 刷屏。单测覆盖不了 MySQL 锁行为，合并率类参数必须过满载验证。

**11. 最后的拐点：Redis 单线程与主库。** 15 万在线时 Redis 单线程 0.93、主库 QPS 到 7.2k 平台、四节点 CPU 0.93～0.97，三者一起指向「加节点是先决条件」。软件侧还能做的是消费扩容与 Redis 按域拆实例。

最终数字：在线 1.3 万拐点 → 5 万贴主库熔断线 → 10 万达成 → 稳态 13 万、峰值 15.3 万，零新增硬件，每千人全栈成本 0.29→0.22 核。

## 三类「口径不可比」误判

技术上每一刀都有埋点实证，但归因上同一天可以错三次。三次形态不同，根因同源：**拿两个不可比的数字做了比较。**

### 一、瞬时点当稳态

一次 `kubectl top` 看到某玩法 81%、房间管理 77%，「拐点找到了」；几分钟后稳态回落到 23% 和 17%。三个相邻的 P99 采样 0.93→1.32→2.79 秒，「单调劣化」；按档位聚合后 800 人档峰值 3.33 秒反而高于 1600 人档的 1.59 秒。爬坡压测有大量结构性瞬态：切档、建桌、建连风暴。**档位统计出来之前，瞬时指标只用于「发现值得看」，不用于「下结论」。** 单调性是最廉价的证伪：8000 人成功率 97.0% 优于 7000 人的 91.9%，真撞墙不会人更多反而更好。

### 二、观测窗口截断

对照实验「池内账号 32 分钟满达成，全新账号只到 75%」——75% 不是达成率，是我在第 5 分钟掐断观测时的值。末段每 60 秒净增 296 人，曲线毫无拐平迹象。采样轮数是脚本参数，稳态达成是系统性质，两者没有关系。汇报表格列了并发、账号数、峰值，唯独没列观测时长——**没进表的维度就等于没被比较。** 同轮还有两条：`--tail=3000` 落日志，错误越密覆盖窗口越短，失败轮里正好最短；代理指标 `login success rate` 在塌陷时被 5 秒重试空转刷高一个数量级，权威计数 `SELECT COUNT(*)` 只有 926。

### 三、被污染的对照

追了一整天的「匹配回归」不存在。压测器背靠背跑，上一轮的对局在托管下要继续打约 20 分钟，同一批账号被判定断线重连、恢复到上一局，等一个早已走远的局面直到超窗。一天里四次把后果当成因：推送 not-found 计数、「恢复旧局=41」、网关会话整批归零……最贵的一次是**摘掉全部本地改动重跑现象依旧，据此排除了自己的嫌疑**——那次对照同样跑在残局窗口里，阴性结果不构成任何证据。先证明环境干净，再做对照。此后压测脚本加了前置门禁：活跃桌归零才开跑。

还有一条属于同一家族：`performance_schema` 的 digest 排行是自实例启动以来的累计量。登录路径 8 类 SQL 4.7 亿次、5.8 万秒，差点立项做登录批量化；两次快照相减取 30 分钟增量，那些 SQL 增量为零，全是七八轮压测打出来的历史。**自己造的负载不要当成用户负载。**

## 教训

- 先埋点再动刀。三刀全部由「差分 / 分段直方图 → 定位 → 最小修复 → 复验」闭环，反例是差点按猜测去做批量查询，而读只占 12ms。
- 异步化有守恒律：订阅异步化只是转移排队位置，下游能力不足时背压必然回传。异步化必须配「worker × 单事件成本 ≥ 峰值事件率」的吞吐对账。
- 扩副本不只是改 replicas：ID 号段容量、连带资源池、Kafka 分区数、打散约束、闸门参数的总量语义，必须同批核对。
- 定性需要聚合量：档位统计、时间序列、多点分布。终止条件必须是系统性质（达标或收敛），固定轮数只能做超时上限，且超时退出只能报下界。
- 对照实验先证明环境干净、各臂参数由同一份配置下发、观测时长进表。跑在被污染环境里的对照，阴性和阳性都不能采信。
