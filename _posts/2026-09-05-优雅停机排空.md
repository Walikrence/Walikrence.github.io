> 背景脱敏：某出海棋牌项目，Go 微服务跑在海外集群的 K8s 上。游戏服有三套引擎：四个传统玩法共用一套核心引擎，德州与百人德州各一套。发版一直用 Recreate 策略，每次滚动都会撕断正在进行的牌局。本文讲的是把「发版即断局」改成「新实例接新局、旧实例打完再退」的全过程，以及一次把定位时间几乎全烧在无效实验上的教训。

## 现象：发版就是一次小事故

旧模式下游戏服的 preStop 只是干等 5 秒，然后 SIGTERM。牌局是有状态的，玩家断开后重连到新实例，局面已经没了。测试环境可以忍，正式服每天数次发版就是每天数次投诉。

更麻烦的是根本不能开滚动更新。滚动意味着新旧两个 Pod 同时存活，而每个游戏服有一个静态注入的 `SERVER_ID`，它既是房间管理服务的路由键，也是注册中心里的实例元数据。两个 Pod 用同一个 ID 注册，会互相覆盖上报的 gRPC 地址，派发指向已死实例。Recreate 正是为了躲这个撞号才选的。

所以「排空」不是一个功能，是三件事必须同时成立：

1. 新旧 Pod 能共存 —— 解决 ID 撞号；
2. 旧 Pod 停接新局、等在局的真人桌打完 —— 排空本身；
3. `terminationGracePeriodSeconds` 必须大于排空上界 —— 否则等到一半被 SIGKILL，比不排空更糟。

## 设计

### 号段租约池：让两个实例不撞 ID

在框架加载配置之前，进程从 Redis 租约池领一个 ID：以配置的基准号为起点、在连续号段里顺序抢占第一个空闲位，租约带 TTL 并定期续期，退出时只释放属于自己的键。选顺序而非随机，是为了让常驻实例总拿号段首位，ID 可读、可运维。未配置号段大小时整个模块是空操作，沿用静态值，便于逐环境灰度。

这个池后来在压测里出过一次「双主」：12 个游戏服 Pod 有 8 个租约键蒸发而进程不知情，因为旧版续租不校验 `Expire` 的返回值——键不存在时 Expire 恒失败且无人知晓。后启动的 Pod 把这个 ID 当空位领走，同玩法同 ID 双主，房间管理侧的连接池地址每秒震荡、补位失败 4900 次/分钟。修法提炼成四条：续租必须校验返回值与 owner；键蒸发要当拍用 SetNX 原子抢回；被他人合法持有就 fail-fast 退进程；TTL 要容忍 Redis 重启窗口。

### /drain 端点：等待放在进程外

排空逻辑抽成一个共享包，三套引擎只注入差异部分：

```go
type Config struct {
    // 仍有真人在座的桌数。preStop 按它是否为 0 决定放行，
    // 必须能在 HTTP 协程上安全调用——不得遍历桌 actor 私有的裸 map。
    HumanDesks func() int
    // 停新进：RM 注销、撤空位广告等，由各引擎自己实现。幂等。
    StopIntake func()
    // 就绪门，排空时摘掉
    Ready *health.Gate
    // 可选：桌总数（含纯机器人桌），仅供排查
    TotalDesks func() int
}
```

两个 GET 端点：`/drain` 触发（幂等，preStop 可能重试），`/drain/status` 查进度。用 GET 是因为运行时镜像是 alpine，busybox 的 wget 发 POST 各版本行为不一。

关键取舍是**等待不在进程里**。框架的 `closeWithTimeout` 硬编码 30 秒，任何写进 `Close()` 的长等待都会被超时跳过。所以等待由 preStop hook 承担：

```
preStop:
  wget /drain            # 停新进
  loop 至多 drainMaxSeconds:
    wget /drain/status   # 每 2s 轮询
    human_desks == 0 → 放行 SIGTERM
```

状态 JSON 的字段名是 preStop 脚本的契约，改名等于让脚本永远等不到放行。`total_desks` 用指针加 omitempty：没注入回调的引擎不出该字段，而不是出一个恒为 0 的假值——0 是合法桌数，分不出「没有桌」和「没统计」。

### 可观测与告警

指标不另起定时器，就在 `/drain/status` 的响应里顺带刷：preStop 每 2 秒打一次，天然就是排空期唯一需要高频观测的窗口。两条告警：排空时长超过 600 秒软上界（说明该玩法对局时长分布超出上界，要调参而不是忍着）；持续排空态超过 20 分钟（多半是某桌永远打不完，或 `human_desks` 口径失真）。

有一个细节差点废掉整套告警：`elapsedSeconds` 在未排空时必须返回 0。否则「排空超上界」会在所有正常实例上恒为真。

### 按玩法金丝雀铺开

四个核心引擎玩法先在测试环境 A 开 RollingUpdate + maxSurge 1 + 号段池 + 排空，上界 600 秒、宽限期 660 秒。德州没有 ID 覆写、号段池可用，同待遇。百人德州最特殊：它的 ID 按房间分片显式注入，直连路径绑在 Deployment 上，两个 Pod 共享同一路径会把直连路由到错的实例，所以保持 Recreate、只做排空，语义改为「等当前这一局结算完」，上界压到 120 秒——判据一旦失灵 2 分钟就暴露，而不是白等 10 分钟。

## 单信号误导：百人德州那一次

百人德州首版上线后排空必撞满 120 秒再被 SIGKILL，比改造前还慢。

根因很短：裁定的语义是「等这一局结算完**且不开下一局**」，我只实现了「等」。有活跃玩家时百人局一局接一局，上一局刚把 `inRound` 置 false，下一局立刻置回 true，判据归零的窗口只有毫秒级，preStop 每 2 秒轮询撞上的概率近似 0。代码逐行 review 看不出问题，因为缺的是「另一条路径会把它改回去」。

但定位它的时间几乎全花在无效实验上。前两个假设都是只盯排空判据一个信号想出来的，全错。真正有效的是同时采样两个来源：排空判据加上 GM 报的对局相位。相位一路从「闲家追加注期」走到「庄家行动轮」——**局根本没卡，卡住的是判据**。单信号下「被观测对象停了」和「观测它的指标坏了」读数完全相同。

同一个验证做了四次才拿到能下结论的数据：第一次固定等 25 秒采样，玩家早已离场；第二次 rollout 换了 Pod，port-forward 还指着旧的；第三次加了有效性自检但用的是 `grep 错误字符串`，日志为空恒通过——**我写的有效性检查正好掉进它本该拦住的那类假绿**；第四次对照信号走 GM，而 GM 在两个实例间轮询，单次读数有一半概率来自不持有该玩家的实例。

修复后正式服实测：判据 1 保持 41 秒（等这一局），归零后玩家仍坐在桌上、判据持续为 0 达 132 秒（不开下一局生效），冒烟客户端全程存活。止开关被结构性单测钉住：每处 `EndRound()` 后 4 行内必须有 `SetInRound(false)`。

## 教训

- 凡「等 X 结束」类的收敛判据，必须同时问「X 会不会立刻又开始」。周期性活动的判据天然会被下一周期重置，只实现「等」不实现「止」，判据永远归不了零。
- 观测到「某状态不推进」时至少要两个独立信号，否则分不清是对象停了还是指标坏了。多实例服务的对照采样要锁定实例，或用「曾观测到」而非「当次观测到」。
- 实验的有效性前提必须被断言，且要求正面证据（进程仍存活、曾观测到目标状态），不能靠「没发现错误」。先判有效性，再读结论。
- 「有意不做」的结论要连前提一起写下。「百人德州有意不开排空」的两条理由后来都被推翻，只读到结论的人不会知道前提早已不成立。
- 租约型资源的续租必须校验返回值与 owner；滚动发布是常态不是异常，每天发生 N 次的路径不能按「偶尔崩一次」评估。
