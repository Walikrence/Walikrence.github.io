> 背景脱敏：某出海棋牌项目，策划在 Excel 里配表，配表仓用 xresloader 按 proto 定义导出 bin/json，服务端和客户端各自消费。本文讲两起「配表错了但没有任何报错」的事故，以及后来立下的表头红线和早暴露机制。

## 现象一：一列 `blue` 落进了 bool 字段

锦标赛配置表的「基础配置」sheet，从第 8 列起数据整体左偏了两列。也就是说，本来该填在第 10 列的值出现在了第 8 列，每一行都是。这个错位至少从一个多月前就存在。

按理说这种整列错位应该很显眼，但它躲过了导表、躲过了服务端加载、躲过了客户端渲染。最隐蔽的一处：本该填在颜色列的 `blue`，落进了旁边一个 bool 类型的「版本向下兼容」字段。

xresloader 的处理方式是：**任何非空字符串转 bool 都得到 `true`**。不报错，不告警。导出的 json 里 `VersionCompat: true`，看起来完全正常。旁边的「进度条颜色」字段拿到了本该属于另一列的 `all`，而它在 proto 注释里的合法取值是 `blue/red/green/gray/orange`，但字符串字段谁都不会去校验取值域。

如果那一格是空的，导出产物里会出现一个明显的空值，反而会有人注意到。**静默转换出来的假数据没有任何异常信号**，这比留空更危险。

## 现象二：加了个合并表头，整个文件存不了

另一起在角色本体表上。有人为了好看，在第一行加了一段 `A1:H1` 的合并单元格作为大标题。配表编辑器逐格写入时撞上只读的 `MergedCell` 对象，整个 xlsx 的**任意 sheet** 都保存失败，而错误文案一律是「Excel 被占用」，把排查带偏了整整一轮。

这个裸写路径从工具初版起就在，四个月后才因为一个合并单元格引爆。

## 排查：判据在 proto 注释里

第一起事故定位时没有靠猜。proto 里每个字段都带注释写明取值域：颜色字段写着 `blue/red/green/gray/orange`，筛选字段写着 `all/high_value/non_high_value`。拿这两个「标尺」去量数据，发现两个合法值都待在左边两格的位置上，**偏移量完全一致**——这是整列错位，不是个别单元格填错。

顺着错位往上追，源头是表头结构不规范。这个项目配表的标准结构是三行：

```
第 1 行  中文列名（给人看）
第 2 行  proto 字段名或 field_alias（xresloader 按名匹配）
第 3 行起  数据
```

xresloader 靠第 2 行的字段名和 proto 对齐。第 2 行一旦写错，对应列**不报错、只静默丢列**——实测有一张表的 `DescKey` 整列从来没被导出过。第 2 行如果整体少写或错位一格，数据就整列平移，而下游只会看到「值有点怪」。

## 同一个模式的第三种长相：bin 与 proto schema 错位

配表侧的错位有一个服务端侧的孪生兄弟。策划在管理后台改了金币场的倍数配置，服务端加载日志显示 bin 已加载、条数正确，但结算仍用旧倍数。

原因是同一个 bin 文件存在两套可解析的 proto schema：服务端 schema 里 `Command` 是 `repeated StrKV`，客户端 schema 里是 `string`。注册代码错用了客户端 schema。两种定义下这个字段的 tag 都是 length-delimited wire type，`proto.Unmarshal` 一声不吭地把第一条 StrKV 的原始字节整块当字符串读进来。应用层看到「Command 有 1 条，值是一坨带控制字节的乱码」，所有倍数查询全部走默认分支。

把真实 bin 用两套 schema 并排解析，结果一目了然：

| schema | 解析结果 |
|---|---|
| 客户端 `string Command` | 1 条，`\x0a\x08roundMul\x12\x0b3:1,4:1,5:2`（一条 StrKV 的完整 proto bytes） |
| 服务端 `repeated StrKV Command` | 5 条：`zl=10` / `theme=...` / `multiWin=400000` / `maxRound=10` / `roundMul=3:1,4:1,5:2` |

顺手扫了全仓 75 个服务端 bin 注册，35 个仍在用客户端 schema，机制上全是同型隐患。

三起事故的共同点是：**错误在类型边界上被「兼容地」吞掉了**。bool 吞字符串、字段名匹配失败吞整列、wire type 相同吞 schema 差异。

## 关键机制：把「静默」变成「报错」

后来立的规矩分三层，每一层的思路都是同一句话：找到那个静默吞错的点，让它在那个点上炸。

**表头红线。**第 1 行必须逐列中文名，第 2 行必须英文 proto 字段名，禁止合并单元格。合并单元格直接报错 400，不允许「跳过合并格照常保存」——跳过意味着用户以为存上了实际丢数据。写任何容错分支前先问一句：跳过之后用户会不会以为成功了？会，就必须报错。

**bool 列门禁。**一个脚本从转换清单反查每个 sheet 对应的 proto，解析出所有 bool 字段，逐行校验取值只能是 `0/1/true/false/yes/no/是/否`。全仓 196 个 sheet 跑一遍，只命中那一处真实病灶，零误报。第 2 行字段名同样校验：归一化后必须能在 proto 里找到对应字段或别名，找不到就拦。

**schema 静态审计。**服务端注册配置时，在泛型擦除前记录 proto 的 `FullName`，一条测试把所有注册跑一遍，断言 `svr_*.bin` 的 proto 必须来自服务端包。存量 35 项进白名单只减不增，新增错配直接 CI 失败。

还有一条门禁的门禁：第一版表头检查只认「A1 是 `#` 且整行其余为空」这一种违规长相，第二天就被「注释写在 B1」和「尾部还留着别的中文」两个变体绕过，且全量门禁报通过。改成**断言正确形态**（逐列必须有非注释中文名）之后才堵住。门禁写成匹配某一种违规长相，必然被下一个变体绕过。

门禁只校验本次推送区间，不跑全量——否则别人的存量问题会拦住所有人。

## 教训

- **静默转换比报错危险一个量级。**留空会被看到，`true` 看起来完全合法。凡是「非法输入 → 合法默认值」的转换，都要问一句这个默认值会不会伪装成正常数据。
- **proto 注释里的取值域是现成的标尺。**排查错位时先拿它去量，偏移量一致就是整列问题，不是个别填错。
- **同一份数据不能有两套都能解析的 schema。**wire type 相同不等于语义相同，protobuf 没有 schema 身份校验，得自己做。
- **门禁要断言正确形态，不要匹配违规长相。**违规的变体是无穷的，正确形态只有一种。
- **门禁验收要「造违规断言退出码」，不能只看它打印通过。**钩子里 `while` 走管道跑在子 shell 里 `exit 1` 拦不住，lfs 钩子吃光 stdin，这两种静默失效都是实测踩过的。
