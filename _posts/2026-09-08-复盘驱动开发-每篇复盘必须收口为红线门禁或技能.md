> 背景脱敏：某出海棋牌项目，客户端仓（Unity）与服务端仓（Go）都由 AI 编程代理承担大量开发，人负责裁定与验收。项目里的复盘文档超过一百篇，本文讲的不是怎么写复盘，而是我们给复盘定的一条硬规矩：**写完不算完，必须收口成红线、门禁或技能三者之一**，否则这篇复盘等于没写。

## 问题：复盘写得越多，重复踩坑越多

早期复盘的典型下场是：分析很透彻，「改进建议」一栏写着「加强代码审查」「提高测试覆盖率」「注意消息时序」，然后归档。三个月后同类问题再来一次，翻出旧复盘发现当时已经写过。

根因不复杂：**复盘的读者是人，而下一次犯错的执行者是 AI 代理，它不会去翻 docs 目录**。人也不会——一百多篇复盘没人能记住。所以「写进复盘」在实际效果上约等于「没写」。

## 分析：三种收口形态

我们把预防措施分成三种载体，按拦截力从强到弱排：

| 形态 | 载体 | 生效方式 | 适用 |
|---|---|---|---|
| **门禁** | 脚本 / 测试 / CI 检查 | 机器拦截，不依赖任何人记得 | 能用代码判定的违规 |
| **红线** | 项目规范文件（每次会话必加载） | AI 代理每次开工都会读到 | 需要判断力但能写成一句判据 |
| **技能** | 带触发描述的操作手册 | AI 接到匹配任务时被自动触发 | 场景化的操作流程 |

判定标准只有一条：**这条措施在下一次同类事故发生之前，会不会被自动执行到**。门禁一定会；红线在每次会话开头被加载；技能在任务匹配时被读。写在复盘正文里的建议，三者都不是。

复盘技能里写得很直白：

> 复盘的核心目标不是写报告，而是产出可落地的预防措施。复盘文档是中间产物，skills 和 rules 才是最终交付物。
>
> ❌ 禁止「写完复盘文档就结束」
> ❌ 禁止「改进建议留给用户自己去做」
> ❌ 禁止「预防措施只记录不落地」

## 做法：三个案例，各讲「事故 → 根因 → 收口成了什么 → 后来拦住了什么」

### 案例一：角色解锁头像框「只显示、不发放」，潜伏 21 天

**事故。** 玩家把角色升到解锁等级后，特权面板里头像框从「锁」变「已解锁」，但背包是空的，想穿戴时服务端返回「未拥有」。从上线到报单，整整 21 天。

**根因。** 界面的锁态判定是 `Locked = level < cfg.UnlockLevel`——按等级现算，不查玩家实际持有。配表侧同一张 proto 里，语音包类型有 `ItemId` 列指向道具表，特效类型没有。整条链「配表 → 等级判定 → 界面显示已解锁 → 发道具进背包 → 可穿戴」里唯独「发道具」那一环缺失，而前面每一环看起来都完全正常。没有人偷懒：策划配了解锁等级，美术资源到位，界面真的会变已解锁，提交标题写的是「角色外观与语音分级解锁」——diff 里只有语音。

**收口成了什么。** 三层，一个门禁、两条红线：

- **门禁**：服务端加了一张「留存语义登记表」，每个外观类型必须声明 `Ephemeral` / `ViaItem` / `ViaOwnedList` 之一，一个遍历枚举的单测保证漏登记即 CI 红，报错文案直接向作者抛出那个关键问题：「这东西需不需要在玩家账下留存？」
- **红线一**（写进项目规范）：**解锁态/拥有态判定不得脱离真实持有**。识别信号是「判定表达式里没有出现任何『查询玩家实际持有』的调用」。
- **红线二**：**同一张表里同类字段的不对称 = 漏做信号**。A 类型有 `ItemId` 而同表 B 类型没有、二者却都要发放，这个不对称本身就该触发追问，而不是默认「B 不需要」。

**后来拦住了什么。** 门禁上线当天做了反向验证：故意删掉一个类型的登记，CI 当场报红并打印出那句提问。另外加了一个「会数数的检查」——统计「需留存但没配 ItemId」的条数，收口判据是 12 → 0。这个计数器在配表发布前额外发挥了一次作用：准确区分了「代码没生效」和「配表没同步」，避免往错误方向排查。

### 案例二：跑马灯与成就 Toast「出生即盲」一个月

**事故。** 跑马灯功能上线一个月，三次迭代，没有任何玩家见过它。成就 Toast 同样。

**根因。** 两者挂在排序 200 的 Rolling 层，而大厅所有界面默认开在排序 300 的 Menu 层且带全屏不透明底图，整层被盖死。一个月内所有验证手段——播放状态机、组件 alpha=1、文本探针、服务端命中日志——全绿，因为它们证明的是「代码在跑」，不是「玩家看得见」。直到用户抽中角色亲自盯屏才暴露。

**收口成了什么。** 这次收口在**技能**里，因为它是场景化的操作纪律：

- 大厅 UI 开发技能新增「挂层红线」：想在大厅期间可见的悬浮 UI，禁止裸挂 Floor/View/Rolling 三层，必须挂 Menu 及以上或加 `overrideSorting`。
- 同一技能新增「验收铁律」：新 UI 挂层上线前必须做**色块对照实验**——往目标层挂一个纯色 Image 截图确认可见。状态机全绿不等于玩家看得见。
- 识别信号：「数据全对、日志命中、界面空白」→ 先做色块对照，不要在状态机里继续找。

**后来拦住了什么。** 修复当晚做了横向清剿——枚举三个被架空层的全部挂载点，揪出了第二个受害者成就 Toast。这一步是复盘技能里的固定动作：「只修代码不建预防机制 → 修了 A 场景，B 场景同样出问题 → 全局排查同模式」。

### 案例三：失败原因合并一码

**事故。** 锦标赛弹窗报错「弹出未支持的类型 Id=X」，被误诊成「客户端枚举缺类型」，实际是配表 bin 没同步。更早的入场不足礼包，把「购买超上限」并进了「金币不足」的错误码，玩家越买越超。

**根因。** `if (a != null && Parse(b)) ... else 报错` 这类复合条件，两个根因共用一条错误信息，排查方向被文案带偏。

**收口成了什么。** 一条红线：**失败原因禁止合并一码**。一条错误信息只能对应一个根因；复合条件失败时必须拆成各自分支分别报错，并在文案里点明排查方向。

**后来拦住了什么。** 这条红线的价值在代码审查阶段：AI 代理每次会话加载规范后，遇到复合条件报错会主动拆分。它不是机器门禁，但比写在复盘里可靠一个数量级。

## 复盘模板与流程

模板本身很短，七段：TL;DR、时间线、根因（直接 / 深层）、修复方案（由浅入深，先一句话再代码对比）、经验总结（每条必须是**可执行的动作**，禁止「加强审查」类空话）、改进建议（谁 / 做什么 / 怎么验证，占全文 30% 以上）、预防措施。没有内容的章节直接删，不留空壳。

流程五步：写文档 → 按问题域归档 → 提炼预防措施 → **逐条实施** → 验证闭环。第四步是核心：扫描复盘文档提取所有可执行项，每条建 TODO，分类处理（规范更新 / 代码修复 / 脚本创建 / 技能创建）。需要其他角色配合的标 `[需确认]` 或 `[跳过]` 并写明原因。完成声明必须带实施统计：「规范更新 N 条、代码修复 N 处、脚本 N 个、需确认 N 条」。

规范里有一句写得很硬：「禁止只分析不走完整流程；禁止写完复盘就结束而不实施改进」。口头分析替代标准产出，在这个项目里是违规。

## 教训

1. **复盘的交付物是「能在下次事故前自动执行到的东西」**，不是文档。门禁、红线、技能三选一，写在正文里的建议不算。
2. **能机器判定的一律做门禁**，并且门禁上线当天做反向验证——故意制造一次违规，看它红不红。「无输出 = 零违规」的门禁比没有门禁更危险。
3. **红线必须带识别信号**。「解锁态不得脱离真实持有」配上「判定表达式里没有查询持有的调用」，AI 和人才能在代码里认出它。
4. **修一处必须横向清剿同模式**。跑马灯修完当晚查出成就 Toast，头像框修完顺带查出枚举重排和 VIP 配表错误。
5. **给复盘定完成判据**：实施统计、收口计数（12 → 0）、门禁反向验证。没有这些，「已复盘」只是一个文件名。
