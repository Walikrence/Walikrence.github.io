> 背景脱敏：一个基于 gin-vue-admin 的管理后台。某天整站接口突然全部被拒，页面能打开但登录不了。根因是限流计数器丢了过期时间，从此永久锁死该出口 IP——等多久都不会恢复。

## 现象

管理后台首页正常打开，但所有接口报：

```
请求太过频繁, 请 -1ns 秒后尝试
```

第一反应是「谁在刷接口」。但两个细节对不上：

1. **首页是好的**。静态文件不过中间件，说明服务本身活着，是接口被拒。
2. **`-1ns` 是什么鬼**。如果是倒计时，不该是负数，更不该是纳秒。

第二点才是突破口。

## `-1ns` 从哪来

翻限流中间件的代码：

```go
if times >= limit {
    if t, err := redis.PTTL(ctx, key).Result(); err != nil {
        return errors.New("请求太过频繁，请稍后再试")
    } else {
        return errors.New("请求太过频繁, 请 " + t.String() + " 秒后尝试")
    }
}
```

`PTTL` 的返回值在 Redis 协议里有两个特殊值：

- `-1` —— key 存在，但**没有设置过期时间**
- `-2` —— key 不存在

go-redis 把它们映射成 `time.Duration(-1)` 和 `time.Duration(-2)`，也就是 -1 纳秒、-2 纳秒。再被 `Duration.String()` 格式化，就成了 `-1ns`。

所以这句提示的真实含义不是「请等待 -1 秒」，而是：

> 这个限流计数**永远不会过期**。

## 取证

Redis 在 VPC 内网，本地连不上，起了个一次性任务进集群扫：

```
GVA_Limit<出口IP>      ttl=-1     count=15001
GVA_Limit<集群内IP>    ttl=1220   count=5
```

阈值是 15000。两行数据把问题钉死了：

- 出问题的 key：**没有过期时间，计数 15001**，已越过阈值
- 同一个库里另一个 IP：TTL 正常倒计时，计数正常

后者很关键——它排除了「配置写错了」这种可能。**配置是对的，只有那一个 key 的状态坏了。**

## 根因：TTL 只在出生时设置一次

```go
count, _ := redis.Exists(ctx, key).Result()
if count == 0 {
    // key 不存在：计数 +1，同时设过期
    pipe := redis.TxPipeline()
    pipe.Incr(ctx, key)
    pipe.Expire(ctx, key, expiration)   // ← 唯一一次设置 TTL
    _, err = pipe.Exec(ctx)
} else {
    if times >= limit {
        return errors.New(...)          // 超限：只报错
    } else {
        return redis.Incr(ctx, key).Err()  // 未超限：只累加
    }
}
```

看出问题了：**`Expire` 只在 key 首次创建的那条分支里出现**。后续所有请求走的是 `else` 分支，只做累加或报错，**从不检查 TTL 还在不在**。

于是只要那一次 `Expire` 因为任何原因没生效——pipeline 部分失败、主从切换丢了命令、运维手工动过 key——这个计数就进入了不可逆状态：

```
没有 TTL → 永不过期 → 计数只增不减 → 越过阈值 → 全拒
     ↑                                        ↓
     └────────── 再也没有代码会去修它 ←────────┘
```

而且限流是按 IP 的，办公网整个团队共用一个出口 IP。**一个 key 坏掉，全公司都进不去后台。**

唯一的解法是人工连 Redis 删 key。我们当时就是这么救的。

## 修复：让它能自愈

修复只加了三行判断——超限时顺手检查 TTL，丢了就补上：

```go
if times >= limit {
    t, err := redis.PTTL(ctx, key).Result()
    if err != nil {
        return errors.New("请求太过频繁，请稍后再试")
    }
    repairExpireIfLost(key, t, expiration)   // ← 新增
    return errors.New("请求太过频繁, 请 " + t.String() + " 秒后尝试")
}

// expireLost 判断 PTTL 结果是否为「key 存在但无过期时间」
func expireLost(ttl time.Duration) bool {
    return ttl == -1*time.Nanosecond
}
```

有个容易写错的地方：**`-2` 不能一起处理**。`-2` 表示 key 已经不存在（自然过期了），下一次请求会走首次创建分支重新设上 TTL，这是正常流程；如果对 `-2` 也调 `Expire`，反而会凭空创建一个没有计数的 key。

因为这个判断只有一行、却容易搞混，我把它单独提成纯函数写了单测，把四种情况钉住：

```go
{"无过期时间需补设", -1 * time.Nanosecond, true},
{"key 不存在不补设", -2 * time.Nanosecond, false},
{"正常剩余不补设",   20 * time.Minute,     false},
{"负一秒不补设",     -1 * time.Second,     false},  // -1ns 和 -1s 不是一回事
```

最后一条是防自己手滑：`-1 * time.Second` 和 `-1 * time.Nanosecond` 长得像，量级差十亿倍。

修复后最坏情况是锁一个限流周期（我们配的 1 小时）后自动恢复，不再需要人工介入。

## 教训

**1. 计数器类的状态必须能自愈**

「设置一次，之后依赖它一直在」是个危险假设。分布式环境里任何单次写入都可能失败，而这类基础设施的失败往往是静默的。凡是「只在初始化时做一次」的动作，都要问一句：如果这次没成功，后面有没有机会补救？

**2. 错误提示里的异常值是线索，不是噪音**

`-1ns` 看起来像个显示 bug，直觉是「格式化没写好，不影响功能」。但它恰恰是根因的直接投影——PTTL 返回 -1 这件事本身就是答案。如果当时把它当成显示问题跳过，就会去查「谁在刷接口」，方向完全错。

**3. 对照组比单个数据点值钱得多**

`ttl=-1 count=15001` 单独看，还可以解释成「限流配置太严」。但旁边那行 `ttl=1220 count=5` 一摆，「配置问题」的可能性立刻被排除。取证的时候多捞一行对照数据，几乎不花额外成本，却能省掉一整轮错误方向的排查。

**4. 按 IP 限流要考虑 NAT 出口**

办公网、云函数、CDN 回源，都是很多人共享一个出口 IP。按 IP 做全局计数时，阈值要按「整个组织的用量」估，而不是「单个用户」。更稳妥的是对已登录请求按用户维度计。
