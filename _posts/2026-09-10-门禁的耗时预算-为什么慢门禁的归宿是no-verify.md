> 背景脱敏：某出海棋牌项目的 Unity 客户端仓库，约 6.5 万个文件。因为没有可用的 CI runner，架构红线（文件 ≤ 300 行、程序集不得反向依赖、协议类型不得进 View 层等）全靠本地 `pre-push` hook 里 38 个 Python 脚本执行。本文讲这套门禁两个月里的耗时治理、它逼出来的绕行设计，以及最后为什么裁定默认不执行。

## 现象：优化速度被新增速度抵消

8 月 17 日一天之内，我优化掉六项门禁的耗时，累计省下几十秒。同一天，别人往 pre-push 里加进了三项新门禁。总耗时始终卡在 45～52 秒。

这不是某一项慢的问题。没有预算约束，提速就是往一个不断变大的坑里填土。

而慢门禁只有一个归宿：`git push --no-verify` 成为习惯。一旦成习惯，门禁就形同虚设——而且绕过时埋点也不执行，在看板上长得像「没人推送」，连「门禁被绕过了多少次」都无从统计。

## 排查：慢在哪

### 测耗时必须用串行数

第一件事是把并行去掉。pre-push 里 38 项默认按 `nproc` 并发跑，同一个纯文档提交的区间实测：

| 并发 | 总耗时 | 最慢单项 |
|---|---|---|
| 1 | 77.0s | `check_accessibility` 9.3s |
| 4 | 66.2s | 同一项劣化到 22.7s |
| 8 | 50.8s | `check_proto_artifacts` 23.0s |
| 16 | 47.3s | 同上 22.7s |

瓶颈是磁盘 IO 与 6.5 万个文件的遍历，不是 CPU。并发只是用「每项都变慢」换「总时间变短」，到 8 路见顶。更要命的是**并发下的数字不能拿来选优化对象**：`check_asmdef_deps` 单独串行 0.18 秒，并发下 12 秒，放大 66 倍。照着并发数字去优化，会去优化一个 0.18 秒的脚本。

所以规矩是 `GATE_JOBS=1 GATE_PROFILE=1` 跑一次，看串行数。

### 头号病灶：重活跑在增量判断之前

传了 `--changed-only` 不等于省了工作量。头部耗时的门禁全是同一个病：最贵的那一步跑在增量过滤之前。一共实证六次：

| 门禁 | 病灶 | 效果 |
|---|---|---|
| `check_accessibility` | 先读完全仓 .cs 收集 internal 类型，再过滤区间 | 22s → 0.46s |
| `check_proto_artifacts` | 压根没接增量参数，每次 rglob 整个服务端仓 | 21s → 0.82s |
| `check_doc_symbol_drift` | 外层符号、内层文件，全仓 .cs 重读 N 遍 | 17s → 4.1s |
| `check_module_deps` | 先建全量 GUID 索引，后做增量过滤 | 4963ms → 389ms |
| `check_no_svr_bin_registration` | 无条件 rglob 3120 个 .cs | 2337ms → 445ms |
| `compile_check` | 无条件先建全仓 asmdef 依赖图，而它只在遇到删除的 .cs 时才用得上 | 11.4s → 985ms |

第六项最能说明这个坑有多隐蔽：区间 `.cs` 数为 0、门禁明明打印「无需编译校验」，却仍然是全场最慢的一项。修法都是一句话：**先问「本次区间可能影响结论吗」，再决定要不要干重活**。

```python
from _changed import range_touches
if range_touches(rev_range, "*.cs") is False:
    print("本次推送未触及 .cs，跳过")
    return 0
expensive_global_index()   # 重活放在判断之后
```

`range_touches` 刻意不过滤 A/M：删掉一个把某类型声明为 public 的文件，会让别处的 internal 声明生效而凭空产生新违规，只看新增/修改会漏。

## 关键机制

### 必须有全局视野的门禁：文件级缓存

有些门禁天生不能只扫改动文件——判断某类型是不是 internal 必须看全仓声明。「区间没碰 .cs 就跳过」只在纯文档提交时有效，而主干推送通常都有 .cs，所以它一度仍要 12.5 秒。

解法是按 `(mtime, size)` 缓存每个文件的解析结果，只重解析真正变过的文件，全局集合从缓存求和：

| 阶段 | 耗时 |
|---|---|
| 纯全量 | 15.8s |
| 缓存命中 | 2.46s |
| merge / checkout 之后第一次 | 7.1s（大量 mtime 变，部分失效，属正常） |

配套把文件列表来源从 `os.walk` 换成 `git ls-files`：3.03 秒变 0.14 秒，git 读索引不碰目录树。但要自己补两个语义——跳过目录的过滤，以及 `--others` 带上未跟踪文件，否则本地新建未提交的 .cs 会漏扫。

缓存最危险的失效模式是「结果悄悄变了但没人发现」，所以加缓存必须证明三件事，缺一不可：

1. **纯全量 == 首次建缓存 == 缓存命中**，比对的是集合内容不只是数量
2. 新文件（不在缓存里）能被解析到——否则新代码的违规永远漏
3. **改动已缓存的文件后，缓存正确失效并抓到新违规**——这条最容易写错

第三条要造探针：先让一个合规文件入缓存，再改成违规版，确认被拦。

### 预算：单项串行 ≤ 2 秒

有了这些手段之后才定得下预算：**新增门禁单项串行不超过 2 秒**，超了先做增量化或缓存，再进 pre-push。这不是洁癖，是前面那个「优化被新增抵消」的直接回应。最慢 3 项被设计成默认就打印，让长尾始终可见。

### 绕行评估：合规正道的成本必须低于绕行成本

耗时之外还有一类更隐蔽的失效：**要求太严逼出错误**。这个仓库里实证了三种：

- 一个管理类顶在行数基线 2729/2729，加分部文件直接变 2786 顶红。于是改成新建独立静态类订阅宿主事件再对外转发——宿主一行不改。同一手法零成本复用了 4 次，产出 4 个转发器类。
- partial 拆分被行数门禁堵住之后，再加一个「partial 总行数」门禁——古德哈特螺旋。
- 为凑 300 行硬拆内聚类成贫血类。

判据是一句话：**审查时发现「某结构存在的唯一理由是让某个数字达标」，就是绕行设计——修门禁而不是留结构**。这样的规则不配阻断，进警告名单或不进 pre-push。

### 行数门禁降级为警告之后

行数类门禁转非阻断三天，超标文件从 2 涨到 40，超出合计 1754 行，78% 来自一个仍在迭代的模块——它前一天刚收口过一次（拆了 13 个类），又被后续 9 个提交推回去。「不拦 = 每天新增 6～20 个超标文件」，清扫追不上新增。

但用户的裁定是**维持非阻断，靠日报与人工清债**。阻断的代价（绕行设计、`--no-verify` 成习惯）已经被证明比债务本身更贵。

## 终局：默认不执行

减负走了三轮：

| 时间 | 措施 | 剩余成本 |
|---|---|---|
| 08-19 | 全局非阻断：跑但不拦 | 前台仍等 31～77 秒 |
| 08-24 | 全部 post 化：转后台异步，前台 exit 0 | 后台仍扫 6.5 万文件，与 Unity 争磁盘 IO |
| 08-31 | 总开关默认关闭：连 fork 都不做 | 0 |

第二轮的直接触发是 GUI 推送被 pre-push 里一次同步 `git fetch` 卡了几分钟；第三轮的理由是后台进程仍与编辑器争 IO——推送不该为门禁付出任何时间。

主干质量的唯一兜底改为每日全量巡检 37 项、出日报加飞书简报。它是独立计划任务，不走 hook。门禁的定位从「推送前拦截」彻底变成「每日体检」。

代价如实记录：埋点断流，看板不再有新数据；半截提交不再被 `compile_check` 在推送前拦下（30 天内它真拦过 32 次），改由推送后编译红暴露。门禁脚本、基线、埋点代码一行未删，改一个默认值即可整体回滚。

顺带一个坑：单项自查在 Windows 控制台曾经一跑就崩——门禁结论行带 emoji，GBK 编不了，通过与不通过两个分支都在打印结论时抛异常、退出码恒为 1。38 项里 24 项缺 UTF-8 兜底。经 hook 的路径有 `PYTHONUTF8=1` 不受影响，被打死的是开发者想查「我到底违规在哪」的那条自助通道。门禁唯一的自助修复通道断了，存量违规因此没人动。

## 教训

1. **耗时是门禁的存活条件，不是可选优化**。慢门禁的唯一归宿是 `--no-verify` 成习惯，绕过时埋点一起跳过，看板上长得像没人推送。
2. **给新门禁定预算（单项串行 ≤ 2 秒），否则优化速度永远被新增速度抵消**。测耗时必须串行，并发数字会把 0.18 秒放大成 12 秒。
3. **头号病灶是重活跑在增量判断之前**。传了增量参数不等于省了工作量，先问「本次区间可能影响结论吗」。
4. **加缓存必须做三条验证**：全量 == 首建 == 命中（比内容）、新文件能解析、改动已缓存文件后正确失效。
5. **合规正道的成本高于绕行成本，就必然逼出绕行设计**。转发器类、partial 拆分、贫血类，都是让数字达标的结构；这样的规则修门禁，不留结构，也不配阻断。
