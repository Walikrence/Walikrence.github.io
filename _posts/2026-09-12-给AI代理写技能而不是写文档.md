> 背景脱敏：某出海棋牌项目，客户端仓（Unity）与服务端仓（Go）由 AI 编程代理（Claude Code 为主，Cursor / Codex 并行过一段时间）承担大量开发。项目里维护着一个近百个条目的技能库。本文讲技能和文档的本质区别、四阶段强制工作流、触发描述怎么写，以及这个库是怎么治理的。

## 问题：文档写了，没人读

项目早期有大量开发规范文档：编码规范、协议兼容性、配表接入流程、Unity 模块依赖。它们的共同命运是：写完之后，人和 AI 都不会在需要的时候想起来读。

一次凭经验写 SQL 的返工复盘统计过：**7 个错误全部有现成文档覆盖**，全部因为没读。文档的生效机制是「有人想起来去读」，这个机制在人身上就不可靠，在 AI 代理身上是零——它不知道 docs 目录里有什么。

## 分析：技能 = 带触发描述的操作手册

技能（skill）在形式上就是一个目录下的 `SKILL.md`，YAML 头只有两个字段：

```yaml
---
name: 提交完整性自检
description: 当提交/推送涉及新建文件的重构（拆分部文件/收敛注册表/搬代码到新文件），
  或删除 .cs/proto/整文件时使用。当提交后他人报编译红、CS0103/CS0246 悬空引用、
  "文件漏交"、half commit 时使用。
---
```

和文档的唯一本质区别是那个 `description`：**AI 接到任务时，先拿任务和所有技能的描述做匹配，命中的技能正文被加载进上下文，然后才动手**。文档靠人想起来读，技能靠描述被触发。项目规范文件里写得很绝对：「在任何响应或行动前，先检查是否有适用技能，哪怕只有 1% 可能」。

所以技能库的价值不在正文写得多好，在于**触发是否准确**。

## 做法一：四阶段强制工作流

所有涉及代码改动的任务，第一步必须读 `标准开发工作流` 技能，走四个阶段：**理解 → 计划 → 实现 → 验证**，不可跳过，不可合理化跳过。

- **理解**：用自己的话复述任务，列出歧义。「显而易见的任务」也要一句话复述。
- **计划**：写计划之前必须先读领域技能——UI 任务读 MCP 侦察技能，协议任务读 Proto 集成技能，游戏逻辑读 Go 专家技能。复杂任务（4 个文件以上）写成计划文档并获得批准。
- **实现**：按计划执行，遇到 bug 切 `系统化调试`，4 个以上可并行子任务切 `并行开发`。
- **验证**：五步——编译、测试、7 项自审、文档同步、带证据的完成声明。禁止「应该没问题」「看起来正确」。

技能正文里有一张「防合理化」表，专门堵 AI 最常用的借口：

| 借口 | 现实 |
|---|---|
| 「任务很明显」 | 明显的任务也需要验证 |
| 「用户说了直接做」 | 指令说的是 WHAT，不是 HOW |
| 「只改一个文件」 | 一个错误改动也能搞崩系统 |
| 「我很熟悉这个代码库」 | 熟悉 ≠ 当前状态已验证 |

这张表是「测出来」的：先在没有技能时让代理跑压力场景，记录它用的确切合理化说辞，再针对这些说辞写技能，然后验证它遵从。编写技能的技能把这个过程叫**文档的 TDD**：没有先失败的测试，就没有技能。

## 做法二：触发描述怎么写

技能库最反直觉的一条规则：**描述只写「何时使用」，绝不概括技能做什么**。

原因是实测出来的。一个执行计划的技能，描述写成「任务间做 code review」，结果代理只做了一次 review——尽管正文流程图明确画了两次（规格合规 + 代码质量）。描述改成只写触发条件「Use when executing implementation plans with independent tasks」之后，代理才正确读了正文。**概括工作流的描述会变成一条捷径，正文沦为被跳过的文档。**

写好一条描述的要点（我们叫 CSO，Claude 搜索优化）：

1. **触发词**：用户会说的原话——「加个红点」「发 MR」「跑冒烟」「UI 改版」。
2. **场景与症状**：错误消息、文件路径模式、症状词——「CS0103 悬空引用」「Response data is null」「一闪而过」。
3. **否定条件**：什么时候不用，防止和相邻技能撞车。比如 `系统化调试` 写明「根因尚未定位时用；已定位且改动区域历史修过时改用 `回归防护`」。
4. **中英双语**：便于匹配，但不概括流程。
5. **控制长度**：所有技能描述的总和有预算（约 3 万字节），超了列表会被截断，截断直接损害触发命中率。

## 做法三：技能的分类

近百个技能大致分十类：工作流（标准开发工作流 / 头脑风暴 / 编写计划 / 完成前验证）、调试（系统化调试 / 回归防护 / UI 闪现跳变诊断）、测试（测试驱动开发 / 三通道冒烟 / 客户端算法测试）、Git（Git 规范 / 工作树 / 提交完整性自检 / 同步主干）、多仓（多仓库并行开发 / 仓库结构）、冒烟（MCP 登录打牌冒烟 / 模拟器 APK 冒烟 / 真机验证）、门禁（架构门禁速查 / 变更测试门禁 / 命名空间校验）、配置（新增配置 / 配表修改流程 / 拉取后再编辑）、协议（Proto 消息集成 / 协议同步 / 协议只读）、画图（archify）。

其中有一对结构值得单独说：**门禁 + 手册的分工**。同一件事（比如 UI 修改前必须先用 MCP 侦察预制体真实结构）会拆成两个技能——一个是短小的英文名门禁技能，被 harness 的 PreToolUse 钩子硬引用，操作 `.prefab` 时弹提示；另一个是中文名的完整手册。审计时子代理曾判断「两者重复可合并」，实读发现是有意分工：门禁要短、要能被钩子引用；手册要全。**合并前必读实际内容，「XX 是 YY 子集」的判断常常不准。**

## 做法四：治理

技能库不治理会腐烂，我们踩过的坑和对应的措施：

- **死链**。一次盘点发现技能入口表列的 10 个后端技能里 7 个在本仓库不存在——技能表随仓库模板迁入，目录没有跟着来。措施：一个脚本解析入口表里的所有路径校验存在性，接入迁移检查清单。
- **BOM 导致自动触发完全失效**。13 个 `SKILL.md` 带 UTF-8 BOM，frontmatter 解析失败，清单里描述显示成 `---`，包括强制入口 `标准开发工作流`。检测方法一行：`head -c 3 | od -An -tx1` 等于 `efbbbf`。措施：一个技能门禁脚本检查 BOM、frontmatter、单条描述不超过 700 字节、总预算不超过 36k 字节，写进编写技能的部署清单。
- **预算超限**。137 个技能、描述总计 36555 字符，超过 30000 的预算，列表被截断。措施：把 17 个低频技能设为 `user-invocable-only`（模型列表里隐藏、可手动调用），再调预算系数。
- **审计瘦身**。137 → 103 → 83，删掉的是其他项目的残留（引用了本项目不存在的类和目录）、空壳占位、脚本已丢失的技能、撞名技能。判残留的方法是核对引用的类和路径是否真实存在，不看名字。
- **技能没触发 / 被绕过**。这两句本身就是 `编写技能` 的触发词：优先修描述，不是加更多规则。

## 人与 AI 共用一套手册

这个库最后一个特点：它不是只给 AI 看的。复盘流程、Git 流程、配表接入流程，人也按同一份 `SKILL.md` 操作。原因很实际——如果人的流程和 AI 的流程是两套，两套一定漂移，漂移之后谁也说不清哪套是权威。技能正文里反复出现「单一权威源」这个词，就是为了堵这个。

## 教训

1. **文档和技能的区别不在内容，在生效机制。** 靠人想起来读的东西，在 AI 代理身上生效率为零；带触发描述的手册才会在需要的时候被加载。
2. **描述只写「何时用」，绝不概括「做什么」。** 概括工作流的描述会变成捷径，正文被跳过。
3. **技能要像代码一样测试。** 先在没有技能时观察代理怎么失败，记录它的合理化说辞，再针对性地写，然后验证遵从。
4. **触发链路本身需要门禁。** BOM、死链、预算超限都会让技能静默失效，而且失效的样子和「技能不适用」一模一样。
5. **门禁与手册分工，人与 AI 同源。** 短的给钩子引用，全的给人和 AI 读；两套流程一定漂移，只维护一套。
