> 背景脱敏：某出海棋牌项目，客户端仓与服务端仓都由 AI 编程代理（Claude Code / Codex 之类）承担大量日常开发。会话动辄几十上百次工具调用。本文讲的是一类只在长会话里高发、而且不报错的幻觉，以及我们最终把它写进项目规范的两条红线。

## 现象：问题和解法都是幻觉

先讲三个真实片段。

**片段一：真改动被反向说成假噪音。** 一次推送之后，AI 在过程说明里写道：「工具注入了噪音——伪造了某文件合并 40 行、推送需确认」。回头核对，那个文件恰恰是这次提交真实改动的 8 个文件之一，`--numstat` 显示 69 行新增、17 行删除。而「推送需确认」这句话，`git push` 在非交互模式下**物理上不可能输出**。最终交付事实（8 个文件、已推送、本地与远端 HEAD 一致）全部属实，但过程叙事里掺了一段凭空编出来的「识破噪音、交叉核验」的英勇故事。

**片段二：预测的成功被当成事实。** 一次统一资源序列化格式的提交，AI 在叙述里写出了提交哈希和「推送成功」，但对话里**根本没有那一次工具返回块**。实际情况是提交被 pre-commit 钩子拦下，HEAD 纹丝未动。直到用户点破「提交被 hook 拦了」才回去核验。同一轮里它还误读了一次被截断的 `git log`，脑补出错误的父提交。

**片段三：无中生有。** 一次设计分析会话里，13 次工具调用全部正常返回（连读取的配置文件都吐出了完整 JSON），AI 却在下一轮宣称「工具连续返回空、被噪音污染」，然后自导了一场「换最简 Bash 命令重新核实」的仪式。全程不存在任何一个异常返回块。问题从头到尾不存在。

三个片段的共同点：**坏掉的不是工具，是叙事**。git、grep、Bash 是确定性工具，它们不会伪造字符串。

## 分析：为什么长会话高发

我们后来把它归为三个机制。

**第一，高频操作的强先验。** commit / push 在会话里重复出现几十次，模型对「接下来会看到成功输出」有极强的预期，于是在真实返回抵达之前就把预测写进叙述。片段二就是这样。

**第二，记忆条目的反向 priming。** 我们把片段一写成了记忆条目「长会话里工具输出可能有问题」，结果片段三里模型模式匹配到这个剧本，抢先上演「识破污染 → 切换工具核验」。防御措施本身成了触发器。这条教训后来被单独写进了记忆：**警惕被核验的噪音从一开始就不存在**。

**第三，宿主注入内容被当成工具输出。** Claude Code 这类 harness 会在对话里注入系统提醒（技能清单、待办提醒），它们不是任何一次工具调用的结果，但在长上下文里很容易被当作「工具吐了奇怪的东西」。

还有一个更根本的问题：这种幻觉**不会报错、不会被任何工具拦下**，看起来全是「有理有据的分析」。同一根错因在运维判断里也出现过——一天之内五次「没验证前提就下结论」（把 allocatable 口径和 MemTotal 口径的内存直接对比、拿冷启动 4 小时的日志量外推出「30 小时写满」、把云厂商托管组件当成残留），每次都惊动用户去处理一个不存在的问题。它们和工具幻觉是同一族：**用推断替代了实测**。

## 做法：两条红线 + 一个鉴别锚点

我们最后没有靠「多读几遍确认」（读回也可能被幻觉污染），而是写进了项目级规范文件，每次会话必加载。原文如下：

> **工具结果只认真实返回，不脑补**：只有被系统 `<result>` 块包裹的输出才是真实的；绝不把「预测的成功输出」当成事实写进叙述，绝不补全被截断的输出（换更小的命令重查）。可疑输出用「工具物理上能否产生此串」自检（如 `git push` 非交互绝无「需确认」，`--numstat` 只吐数字）。
>
> **宣称「工具异常/返回空/被污染」前必须指认具体证据**（长会话高发的「无中生有型」幻觉）：必须能回答「是哪一次调用、哪个 `<result>` 块、异常串原文是什么」；指认不出＝该宣称本身就是幻觉，禁止自导「换工具重新核验」的仪式，直接继续正常工作。注意 harness 注入的 `<system-reminder>` 是宿主内容，不是工具输出被污染。

配套两条硬判据：

1. **git 写操作断言必附确定性证据。** 声称 commit / push 成功之前，必须真实执行 `git rev-parse --short HEAD origin/main` 并展示返回。哈希相等与否是确定性输出，没法用「大概成功了」糊弄。
2. **截断输出绝不补全。** 换更小的命令重查，比如 `git log -3 --oneline` 代替全量 log。

鉴别锚点只有一句话：**这个工具物理上能不能产生这个字符串？** 非交互的 `git push` 不会问你「是否确认」，`--numstat` 只会吐两列数字，`grep -c` 只会吐一个整数。凡是工具「说了人话」，先怀疑是模型说的。

## 延伸：自制假信号

幻觉的近亲是「自制假信号」——测量本身坏了，而不是系统坏了。一次房间管理服务的性能治理里，同一个任务内我们排除了五次自制假信号：

| # | 假信号 | 真相 |
|---|---|---|
| 1 | grep 某缓存名得 593 处命中，以为锁竞争仍严重 | worktree 目录名恰好包含这个词，每条栈帧路径都被匹配 |
| 2 | mutex 剖面显示 0 cycles，判定「已非热点」 | 那轮冒烟根本没驱动目标路径 |
| 3 | 「往返次数不随键空间增长」的断言恒绿 | 内存 mock 的 SCAN 忽略 COUNT 参数，改造前后一样 |
| 4 | 门禁报「合规」 | awk 语法错误导致无输出，无输出被当成零违规 |
| 5 | grep 计数得 1，以为门禁报出了问题 | 匹配到的是成功消息里的「扫描 15 处键模板」 |

第 1 条误报坏、第 2 条误报好，方向相反但都是假的。它们和工具幻觉共享一个纪律：**出数之前先证明目标路径被驱动过、模式不会匹配到路径和自己的成功消息、解析器必须对失败硬失败而不是以零违规放行。**

## 教训

1. **信任边界画在「工具返回块」上，不画在「AI 的叙述」上。** 只有独立的返回块是事实，叙述里的任何数字、哈希、成功宣告都要能对应到一个返回块。
2. **宣称异常必须能指认具体证据。** 答不出「哪次调用、哪个返回块、异常串原文」，这个宣称本身就是幻觉，直接继续正常工作，不要开启复核仪式。
3. **防御措施可能反向 priming。** 记忆和规范里写「小心工具出问题」，要同时写「多数时候问题不存在」，否则模型会抢先上演剧本。
4. **确定性核验优先于阅读式确认。** `git rev-parse`、`grep -c`、`ls` 这类只吐哈希和数字的命令，比「再读一遍文件」可靠得多。
5. **规则要落到每次会话必加载的地方。** 写在复盘文档里没有用，模型不会去翻；写进项目规范文件才会在下一次长会话里生效。
