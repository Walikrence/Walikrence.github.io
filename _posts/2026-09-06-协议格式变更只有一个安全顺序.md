> 背景脱敏：某出海棋牌项目，客户端 Unity、服务端 Go，各自独立仓库、独立发布节奏。IM 聊天走一条独立 WebSocket，线格式从 JSON 改为 protobuf 二进制。客户端先合入并出包，服务端的兼容改动还躺在六个未推送的分支里，结果已发布版本的 IM 全链路不可用。本文讲这次事故、一个一眼判定的判据，以及后来在另外两次改造里反复验证的顺序规则。

## 现象：每 100ms 重连一次

某天晚上七点，测试环境服务端日志开始刷同一行：

```
Read Message error: invalid character '\b'
```

每 100 毫秒一次，来自同一个用户。客户端表现是「聊天连不上，要么重试要么退出登录」，连上即断，断了即重连。

第一反应是网络。但这行日志其实已经把根因写在脸上了。

## 排查：`\b` 是什么

`\b` 是 `0x08`。而 protobuf 的第一个字段（field number 1，wire type varint）编码出来的 tag 字节正好是 `(1 << 3) | 0 = 0x08`。

也就是说：客户端在发 protobuf 二进制帧，服务端在拿 `ReadJSON` 解它。JSON 解析器读到第一个字节 `0x08`，报「非法字符」，读循环 return，连接关闭。客户端重连，再发一帧，再断。

这不是网络问题，是**顺序倒挂**：发送方已经切了新格式，接收方还不认识它。

顺着往下查，时间线是这样的：

```
09:48  CI 从服务端同步 proto，客户端里手工放的 Wire.cs 被删，主干编译红
17:54  手工提交「暂时恢复被 CI 过早删除的 Wire.cs」
17:58  二进制上行改动进客户端主干  ← 客户端开始发二进制帧
18:14  「再次恢复被 CI 删除的 Wire.cs」  ← 第二轮循环
19:07  线上 invalid character '\b'，IM 全断
19:2x  服务端集成分支合并部署，双读生效，错误归零
```

服务端那边的改造被拆成了六个分支：proto 拆包、双格式解码、版本闸门、二进制上行、冒烟、清理死代码。它们之间有编译级依赖（一个常量的归属在两个分支里不一样），**合并顺序从来没有被验证过**。分支没合，服务端能力就不存在；客户端却按「服务端已支持」写了代码并出了包。

中间那个 `Wire.cs` 的循环也值得说。客户端的 proto 产物目录是 CI 用 `rm -rf` + 重建维护的，源仓库里没有对应的 `.proto`，CI 就必然删掉它。编译红本该被读作「客户端引用了服务端根本不存在的包」——依赖倒挂的红灯——却被当成「CI 删早了」，用手工恢复把信号按掉了。判据其实一条命令就够：

```bash
git -C <服务端仓> log --diff-filter=A -- "*wire.proto"
# 输出为空 ⇒ 服务端从来没有过它 ⇒ 客户端那份是手工造的
```

还有一个放大器：服务端握手里没有版本字段，解析失败直接关连接。所以协议不匹配的症状是「反复掉线」，而不是「请更新版本」。排查者的第一反应会走向网络。

## 关键机制：谁先动

修复本身不复杂——服务端 `ReadJSON` 改成 `ReadMessage` 后按帧类型分流：

```go
msgType, raw, err := c.ReadMessage()
switch msgType {
case websocket.BinaryMessage:
    err = proto.Unmarshal(raw, &p)   // 新客户端
case websocket.TextMessage:
    err = json.Unmarshal(raw, &p)    // 旧客户端
}
```

**双读**意味着新旧客户端都能连。有了它，客户端什么时候切、切多少比例，都不再是危险动作。

真正要记住的是顺序：

```
         安全                                   全断
 ┌──────────────────┐                  ┌──────────────────┐
 │ 服务端双读        │                  │ 客户端发二进制    │
 │   合并 + 部署     │                  │   合入 + 出包     │
 └────────┬─────────┘                  └────────┬─────────┘
          ▼                                     ▼
 ┌──────────────────┐                  ┌──────────────────┐
 │ 客户端切二进制    │                  │ 服务端仍 ReadJSON │
 │   发版            │                  │ → invalid '\b'   │
 └──────────────────┘                  └──────────────────┘
   中间窗口：旧端走 JSON，新端走二进制      中间窗口：新端全断
```

这条规则其实可以说得更一般：**改线格式时，接收方先具备兼容能力并部署，发送方再切换**。「服务端先」只是因为这次的发送方是客户端。

同一个项目里另外两件事验证了这个一般化的说法。

**反例（更早的心跳事故）**。服务端把心跳解析从自定义二进制全面迁到 protobuf，客户端的清理计划覆盖了所有业务 Handler，唯独漏了底层网络包里的 `KeepAliveMsg`——它用固定消息号、不走常规路由，扫描 Handler 列表时自然跳过。结果客户端还在裸写两个 `uint32`（固定 8 字节），服务端期望 varint 编码的 tag+value，解析失败不回心跳，10 秒超时断连，100% 复现。这次是接收方（服务端）先切、把旧格式的兼容直接砍掉，方向同样倒挂，只是倒在另一侧。

**正例（推送新命令字）**。服务端把成就进度推送从逐条三个命令字聚合成一条批量命令字。推送是服务端主动发、没有版本协商，老客户端收到未知 cmd 走 default **静默丢弃**。所以这次必须**客户端先**具备处理能力，服务端后切：协议 MR（纯增量）→ CI 同步 → 客户端加 case → 服务端切换 MR，旧命令字保留兼容。发送方是服务端，接收方是客户端，先动的还是接收方。

三件事放在一起，规则只有一条，只是主语会换。

### 层叠分支必须先建集成分支

六个互相依赖的分支各自为战，是这次事故的第二个根因。后来的做法是：凡是互相层叠的多个分支，先建一个集成分支按顺序合并，跑 `go build` + 本地 CI，验证通过才逐个发 MR。八天后同一批人做 IM 合流到主网关的改造，服务端 18 个 MR，刻意让客户端改动在服务端合并且部署到目标环境**之后**才推，派发客户端子代理时把「禁止 push」写进 prompt 的硬门，而不是指望它自己判断时机。

## 教训

1. **改线格式只有一个安全顺序：接收方先兼容并部署，发送方后切换**。客户端上行改格式是服务端先；服务端推送加命令字是客户端先。方向反了，中间窗口就是全断。
2. **`invalid character '\b'` 是一眼判据**。`0x08` 是 protobuf field 1 的 tag 字节；服务端 JSON 解析器报它，就是对端在发二进制，不用查网络。
3. **编译红要分「产物缺失」还是「依赖倒挂」**。CI 产物区里的文件被删，先查源仓库有没有它的历史；手工恢复只会进入删除→恢复→再删的循环，还把真正的信号按掉。
4. **互相依赖的分支必须先在集成分支上验证合并顺序**。「各自都能编译」不等于「合在一起能编译」，更不等于「服务端已具备这个能力」。
5. **握手里要有版本闸门**。没有它，协议不匹配的症状是「反复掉线」，把排查引向错误方向。补闸门时缺参一律放行，兼容存量客户端。
