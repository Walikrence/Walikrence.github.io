> 背景脱敏：某出海棋牌项目的管理后台基于 gin-vue-admin 搭建，IP 限流中间件用 Redis 计数。某天海外办公室的同事反馈后台全站 API 不可用，静态页能打开，任何接口都返回一句奇怪的话。

## 现象：请 -1ns 秒后尝试

报错文案是：「请求太过频繁, 请 **-1ns** 秒后尝试」。首页能开，`/api` 下所有接口全挂。

`-1ns` 不是倒计时。它是 Redis `PTTL` 返回 `-1`（key 存在但没有过期时间）被 Go 的 `time.Duration.String()` 格式化出来的结果。所以这句话真正的意思是：**你的限流 key 永远不会过期**。

## 取证

管理后台的 Redis 在 VPC 内直连不到，于是起了一个临时 Job 跑 `redis-cli` 扫 `GVA_Limit*`：

```
GVA_Limit<出口IP>    ttl=-1     count=15001    ← 阈值 15000
GVA_Limit<另一IP>    ttl=1220   count=5        ← 正常
```

同一个库里另一个 IP 的 key 有正常的 TTL 和计数，说明不是配置问题。出问题的 key 没有 TTL，计数已经越过阈值一格，而且只会继续涨。

## 根因：Expire 只做一次

gin-vue-admin 的 `SetLimitWithTime` 逻辑简化后是这样：

```go
func SetLimitWithTime(key string, limit int, expiration time.Duration) error {
    exists, _ := rdb.Exists(ctx, key).Result()
    if exists == 0 {
        // 只在 key 首次创建时设置过期
        pipe := rdb.TxPipeline()
        pipe.Incr(ctx, key)
        pipe.Expire(ctx, key, expiration)
        _, err := pipe.Exec(ctx)
        return err
    }
    times, _ := rdb.Get(ctx, key).Int()
    if times >= limit {
        t, _ := rdb.PTTL(ctx, key).Result()
        return fmt.Errorf("请求太过频繁, 请 %s 秒后尝试", t)   // t == -1 → "-1ns"
    }
    return rdb.Incr(ctx, key).Err()
}
```

`Expire` 只在 key 首次创建的那次 pipeline 里执行。之后每次请求只做 `Incr`，从不补救。只要那一次 `Expire` 因为任何原因没生效（pipeline 部分失败、Redis 主从切换、极端时序），这个 key 就永远没有 TTL：计数只增不减，越过 15000 后该 IP 永久锁死。唯一的恢复方式是人工连上 Redis 删 key。

这个文件是一年多前随框架整体导入的，从未改动，缺陷来自上游。它不是一个高频 bug——需要「首次创建时 Expire 恰好丢失」这一次小概率事件——但一旦发生就是不可自愈的永久故障。

## 修法

两种思路。最小改动是在超限分支里检测并补救：

```go
if times >= limit {
    t, _ := rdb.PTTL(ctx, key).Result()
    if expireLost(t) {                          // t == -1：存在但无 TTL
        rdb.Expire(ctx, key, expiration)        // 补设，最坏锁一个周期后自愈
        log.Warn("limit key lost ttl, re-expired", "key", key)
    }
    return fmt.Errorf("请求太过频繁, 请 %s 后尝试", t)
}

func expireLost(pttl time.Duration) bool {
    return pttl == -1   // 注意：-2 表示 key 不存在，不该补设
}
```

判定提成独立的 `expireLost` 函数是为了单测——项目用 vendor 模式，不想为此引入 Redis mock。`-1` 和 `-2` 必须区分：`-2` 是 key 不存在，补 `Expire` 没意义。

更彻底的写法是把「创建 + 设过期」变成原子且幂等的操作，每次请求都走同一条路径：

```go
// SET NX EX 保证「首次创建必带 TTL」，之后只 INCR
rdb.SetNX(ctx, key, 0, expiration)
n, _ := rdb.Incr(ctx, key).Result()
if n > int64(limit) { ... }
```

`SetNX` 在 key 已存在时什么都不做，在 key 不存在时原子地写入初值和 TTL，不存在「Incr 成功但 Expire 没成功」的中间态。

## 顺手固化的排障配方

这次之后，把判断路径写成了一条固定的检查顺序，放在运维手册里：

1. 管理后台「静态页正常、API 全挂」→ 先怀疑限流，不要先查网关和证书。
2. 报错文案带 `-1ns` → 直接确认是 TTL 丢失，不必再看请求频率。
3. Redis 在 VPC 内不可达时，用 GitOps 起一个带 `ttlSecondsAfterFinished` 的临时 Job 跑 `redis-cli`，扫 `GVA_Limit*` 看每个 key 的 `ttl` 与 `count`；`ttl=-1` 即死锁，删 key 立即恢复。
4. 一次性排查用的 chart 和 Job 用完即删，不留在仓库里——Job 被回收后残留的应用对象会显示 Missing，看起来像另一个故障。

整个链路从「同事报障」到「删 key 恢复」不到半小时，其中大部分时间花在起 Job 上；真正的定位靠那个 `-1ns` 只用了几分钟。

## 教训

- **错误文案里的怪数字是线索，不是噪音。**`-1ns` 直接指向 `PTTL == -1`，比翻日志快得多。
- **「只在首次做一次」的保护逻辑要有补救路径。**任何依赖某次操作必定成功的设计，都要问一句：那次失败了会怎样，能不能自愈。
- **限流器的失效模式要能自愈。**限流是保护机制，保护机制本身把系统锁死是最坏的结果；补 TTL 后最坏也只是锁一个周期。
- **上游框架导入进来的代码同样要审。**「从未改动」不等于「没有问题」，只等于「没人看过」。
