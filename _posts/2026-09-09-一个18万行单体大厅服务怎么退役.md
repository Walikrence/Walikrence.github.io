> 背景脱敏：某出海棋牌项目的服务端有一个「大厅」服务，是历史最久的单体：客户端唯一的 WebSocket 接入点、进房与撮合入队、进厅首屏组包、在线集合、会话续期、定时巡检、下行推送的持连方，全部在它里面。改造目标是把它拆成网关、房间管理、角色三个服务并删除本体。从 7 月初定稿到 8 月中删除，大约五周。本文记录阶段划分、每一阶段踩到的东西，以及删完之后才审计出来的遗漏清单。

## 为什么不能一刀切

摸底时的几个关键事实决定了路线：

- 仓库里没有独立的网关进程，但大厅内部已有一套模块化的网关脚手架——接口、单测齐全，生产零调用，`handleJoinHall` 还是 TODO。
- 客户端只有一条主 WebSocket，地址来自登录回包，所以网关灰度可以由服务端控制、客户端零改动。
- 路由规则存在双份真源：生产在用的分发器带 827 特判、828 冷却、路由防伪造；休眠脚手架里的规则表全缺。任何重写都会丢掉这些补丁。

结论是分阶段：先让脚手架接管主路径，再把「连接态」和「业务态」分离，最后物理拆出独立进程，每步保留回退开关。

## 阶段 A～C：网关独立进程

**A** 激活脚手架接管大厅内部的主读循环，以生产分发器的语义为准对照迁移，禁止重写。
**B** 进厅改两段式，连接注册与业务进厅分离，为跨进程做准备。
**C** 物理拆出独立网关进程，登录回包灰度下发 `/gw` 地址，老的 `/hall` 直连保留为秒级回退网。

C 阶段最硬的一课是**服务发现名的语义平面**。把全部 `discovery:///hall` 迁名到业务大厅后，游戏服到网关的按实例下行推送全部 InstID miss，首屏超时。同一个名字下其实混着两种语义：推送方要找的是「连接持有者」，业务调用要找的是「大厅本体」。迁名前两个平面的成员恰好重合，混用不显形；迁名让它们分离，凡按连接持有者寻址却指到业务大厅的调用全部失效。修法是双平面拓扑：推送到用户平面恒指原名，业务平面走插值变量。

同期还清掉一个多副本才显形的坑：框架把「按实例路由」选项写进 `NewRawClientByInstID` **返回的** ctx，用原 ctx 发调用会退化成随机路由。单副本环境不显形，多副本下被 not-found fan-out 兜底掩盖成「多一跳 + 噪音」，从不报错。全仓修了 3 处，签名层面强制调用方接收返回 ctx。

## 号段直发：一个从未生效的特性

网关绕过大厅、按消息号段直发德州服务的 P4，**从合入起一次没生效过**：网关的 routing 配置缺 game 条目，解析必失败，100% 回退到大厅。回退让业务表现完全正常，冒烟全过，灰度「验证通过」。只有一个指标能区分：`texas_direct_total{result="ok"} = 0`。

补上条目后连带挖出四个问题，其中一个直接决定了后面「会话续期下移」这一步：大厅的 Dispatch 顺带做 `ResetLastOpTime`，是操作时间、登录 Token（30 分钟）、路由键（45 分钟）的唯一续期点，且 EXPIRE-only 过期不可复活。直发绕过后，纯观战会话 30 分钟后 API 鉴权全线失败。**绕过一跳之前，先 grep 那一跳入口函数的副作用，逐条设计替代通路。** 续期从此下移到网关的 keep-alive。

## 阶段 4～6：搬业务，删尾巴

网关稳定后，21 个 MR 把大厅里的业务逐块搬走：

- **进房与撮合入队**（含门票垫付、write-ahead、回滚）迁房间管理服务；
- **进厅首屏组包**迁角色服务，由网关直接取并下发，新增「一次请求多帧应答」协议能力；
- **在线集合写入方**迁网关，删除不可达路径，退役一条只有冒烟在用的消息号。

这一段的教训集中在「迁入方的静默装配」。进房迁入后连续三次部署失败，每次都长得像业务规则错误：恒回「没有权限」，是房间→服务映射在新宿主里从没人填过；恒回 199，是路由配置缺撮合条目；仍回 4039，是新宿主从未调过撮合客户端的 `Init()`，全走禁用桩。三者共同点：不报错、不崩溃，只是功能悄悄不工作。第三条甚至不是本次引入的——离房迁入时就存在，离房照样回成功、玩家却留在队列里，一直没有出口暴露，直到进房迁入才顶出来。

还有一条关于「不要顺手统一刻意的例外」：某支进房错误码原来刻意整值返回、不过 byte 转换层；重构成「先算码、调用方统一转」时把它一起截断成 213，补币礼包弹不出来。而那段注释本身就在讲截断的危害。机器人冒烟一律只断言 `result == 0`，错误码长什么样它不在乎。

首屏开关在正式服打开后，网关与大厅日志两边都是 0 条，看起来没生效——首屏日志是 Debug 级，被生产日志级别整个吞掉。是指标救回来的：`first_screen_total{result="delivered"}` 两个 Pod 合计 6 次。**开关类特性应带一个与日志级别无关的计数指标。**

## 翻默认，删本体

「无大厅模式」开关在各测试环境与正式服逐个打开、稳定观察后翻为默认，随后一次提交删除大厅服务本体与部署。大厅时代的客户端 handler 表从十余个号降到 1 个，最后归零。

## 删完之后审计出来的遗漏

删除后第四天，发布冒烟连红四天才有人看——它挂着 `allow_failure` 且没有通知出口。顺着红灯挖出一批「接口在、客户端在、调用方没了」的断链，编译期与启动期零报错：

| 遗漏职责 | 症状 | 去向 |
|---|---|---|
| 在线时长定时巡检 | 某统计项不再累加 | 网关重建，并补上 mq 模块配置 |
| 登出时间记账 | 最后登出时间不更新 | 网关断开事件接管 |
| 取消匹配的无绑定幂等回执 | 客户端发取消后永远等不到回执，卡在取消中 | 网关按无路由 / 不在本实例两种分支补幂等回包 |
| 断线退出匹配队列 | 退队函数零断线调用方 | 网关按 120 秒窗口异步出队 |
| 桌内消息号段的路由 | 注释写着「仍走 legacy dispatch」，而那套 dispatch 已随大厅删除 | 复查后判定真实客户端走直连不受影响，是冒烟路径与客户端不一致 |
| 跑马灯等下行广播通道 | 持连方消失 | 落在网关的下行队列 |

第一条尤其典型，它分两次才修完：代码搬到网关了，但网关没装 mq producer，事件发送返回「传输未初始化」后经 `sync.Once` 只打一条 Warn 就静默丢弃，巡检日志照常打「完成」。**代码搬了、配置没搬，看起来完全正常。**

另一个放大器是冒烟统计口径：脚本用 `grep -c '^--- PASS'` 数用例，只匹配行首无缩进的顶层用例，子用例的 SKIP 带缩进一条都匹配不到。「顶层 PASS + 子用例恒 SKIP」在报告里完全隐形，零覆盖被报告成全绿。

再往后十天，又补了一轮注释层的同源欠账：网关里描述当前行为却已失真的 6 处注释——「回退大厅，保证不丢」实际是丢弃；「断开事件通知大厅」分支体只剩一行 log；引用的 `keepAliveHall` 函数与文件均已删除。带行为承诺的失真注释最危险，它让后来者跳过验证直接采信。

## 教训

- 删服务必须先做「副作用调用点清单」：被删代码里所有事件发送、客户端调用、定时器、就地回执，逐项写明接管方或确认死代码。靠冒烟事后捞是碰运气——这次有冒烟覆盖的 4 处纯属侥幸，审计又挖出 4 处无覆盖的。
- 有回退兜底的特性，验收判据必须是指标（新路径命中率），不是「业务正常」。失败的表现和成功的表现完全一样时，只有指标能区分。
- 绕过一跳之前先 grep 那一跳的副作用（续期、计时、自愈），每条设计替代通路。
- 迁入方的装配要一次做齐：路由条目、客户端 Init、映射登记、传输层配置。不报错的缺失比报错的更贵。
- 承载者删除时，指向它的注释、已知失败集的旧定性、只验自己的开关测试要同批清理；「仍走 X」「留 X」这类路标必须逐条确认 X 还在。
